## 每日开服检查

想确认服务器可以接人，先看两件事。正常启动或重启之后，在服务器控制台确认出现了 `AceEconomy v2.2.0` 和 `AceLib v1.2.1`，并且只加载了一个 AceLib 版本。接着用一个测试账号执行 `/money balance`，必要时再执行 `/baltop top`。

如果服务器还没准备好，不要对玩家开放。保留最早出现的那条 AceEconomy、AceLib 或存储错误，然后按照[故障排除](troubleshooting.zh-CN.md)处理。

## 选择与确认存储

想知道数据存在哪里，看 `storage.type` 就好，v2 后端由它决定：

| 值 | 位置 | 适合情形 |
| --- | --- | --- |
| `json` | `plugins/AceEconomy/data-v2.json` | 单台服务器，使用本地文件 |
| `sqlite` | 插件数据目录下的 `storage.sqlite.path` | 单台服务器，使用 SQLite 数据库 |
| `mysql` | `storage.mysql.*` | 使用受管理的 MySQL 或 MariaDB 服务的单台服务器 |

SQLite 的路径必须留在 `plugins/AceEconomy/` 之内。MySQL 的 `pool-size` 和 `max-lifetime` 必须放在 `storage.mysql` 之下，密码不要写进共享文档。

所有受支持的后端都使用同一套 v2 账户与交易模型。选错后端多半开机就会报错，做法见[故障排除](troubleshooting.zh-CN.md)。

一份存储只服务一台正在运行的服务器。不要把两台服务器指向同一个 JSON 文件、SQLite 文件或 MySQL 数据库：这种接法不在支持范围内，而且可能在没有报错的情况下分歧。详见[持久化、备份与还原](persistence.zh-CN.md#一份存储只给一台服务器)。

## 安全地修改配置

想改配置又不想把服弄坏，照这套顺序做。只有在你平时的变更流程能保护文件不被写坏时，才在服务器运行中编辑 `plugins/AceEconomy/config.yml`。修改前先复制一份，保留 `version: "2.0"`，并在套用前确认 YAML 结构正确。

普通的配置或语言变更，请从控制台执行：

```text
/aceeco reload
```

成功时会回显 `AceEconomy reloaded`。如果新的配置或语言文件加载不了，插件会保留最后一份有效的内存快照，不会用半成品配置顶替。但如果你改动了 `storage.type`、SQLite 路径、MySQL 连接值、插件 JAR、AceLib 或可选插件，就必须完整停服再启动，只做重新加载不够。

重新加载是一整笔交易：配置、语言、货币、银行界面四组候选会先各自验证，全部通过才一起换上。任一组失败就什么都不换，服务器沿用旧配置继续跑。

货币修改会在交换前先分类：

| 变更 | 重新加载怎么做 | 为什么 |
| --- | --- | --- |
| 没变 | 重新加载成功，什么都不换。 | 没有东西要套用。 |
| 只改 `name` 或 `symbol` | 直接热套用，新显示文字立刻全服生效。 | 显示文字不影响已存金额、小数位数与默认货币。 |
| 新增货币 | 重新加载拒绝并告知新增的 ID，服务器沿用旧组合。请重启才会生效。 | 既有账户需要批量初始化并支持回溯，目前没有存储后端能做到。 |
| 删除货币，或改 `scale`、改 `default` | 重新加载拒绝并告知受影响的 ID，服务器沿用旧组合。请重启才会生效。 | 这些变更会让已存余额被误读或变成孤儿。 |
| 候选区块格式无效 | 重新加载拒绝并告知解析原因，什么都不换。 | 读不懂的候选配置绝不能取代线上登录表。 |

有三个设置只能重启，不会被重新加载套用。`settings.main-command-alias`、`storage.type`、`leaderboard.enabled` 如果和运行中的值不同，重新加载照样成功，但回报会多一条点名的重启提醒；线上值保持不动，下次完整重启才会换。

回报会告诉你发生了什么事。失败时显示拒绝理由，例如哪个货币 ID 被新增、哪个小数位数被改，让你知道该修文件还是排重启。成功时附加备注：哪些已热套用（显示文字、布局、配置与语言），哪些还要重启。

成功的重新加载会用新布局把已打开的银行界面原地重建并重开，不让任何点击卡在新旧规则之间；玩家不用重开 `/bank`。重建或重开失败的界面才会关闭并告知玩家，关闭与告知皆为 best-effort。跟重新加载撞期的打开会等交换完成，不管排在交换前后，建出来的都是当前布局。这是正常现象，不是东西坏了。

同一次重新加载也会清空整个同步余额缓存。这是预期的接受行为，不是 bug，余额不会真的不见：Vault 读取绝不阻塞等待存储，所以在下一次已持久化的读取或成功写入重新填入之前，余额查询会回到安全默认值 `0.0`。不会在调用线程上同步回填，因为那会把缓存原本要避开的阻塞 I/O 带回来。看到短暂的 0 先等一次正常读写，不用急着还原或重启。

不要把 Bukkit 的 `/reload` 当成维护或升级的捷径。

## 日常指令

检查运行中的服务器时，可以使用这些格式：

```text
/money balance [player] [currency]
/pay send <player> <amount> [currency]
/withdraw cash <amount> [currency]
/baltop top [currency]
/bank open
/aceeco give <player> <amount> [currency]
/aceeco take <player> <amount> [currency]
/aceeco set <player> <amount> [currency]
```

请用一个测试账号做小额、可回退的检查，不要直接改动真实玩家的余额。管理员调整余额时，请记到服务器平时的管理记录里。指令打错就对照[指令与权限](commands.zh-CN.md)的错误表。

## 备份与还原

受管的逻辑快照和手动的灾难恢复副本是两套不同的流程，不要把其中一种的说明当成另一种来用。

### 手动文件与数据库灾难恢复

想自己留一份文件级副本保命，先停服再动手。直接复制 JSON 或 SQLite 数据文件之前，必须先停服。手动副本要放在正式插件目录之外，文件名带上日期和用途，也不要覆盖唯一一份确认正常的副本。这属于文件级的灾难恢复副本，不是受管的 `/aceeco backup` 指令。

MySQL 或 MariaDB 的原生／物理备份，请按数据库管理员平时的备份流程来做，并和对应的服务器配置备份一起保存。原生或物理的数据库备份不等于受管的 v2 逻辑快照。目前本文还没有验证过真实的 MySQL/Folia 组合与灾难恢复流程；在正式依赖之前，请先在一次受控演练中确认可行。

### 受管指令

想在不停服的情况下留一份可还原的记录，控制台和获得授权的管理员可以这样做：

```text
/aceeco backup [label]
```

这条指令在服务器运行中就能执行。它会在插件控制的 `<plugin data folder>/backups/` 目录下，写出一份不含任何凭证的 v2 JSON 逻辑快照。写入时，系统会先以「不存在才建立」的方式生成 `<backup-id>.json`，把完整内容写进去，再以同样方式生成 `<backup-id>.ready`。这个 `.ready` 文件里含有 SHA-256 校验和，是整份快照「正式生效」的标记；还原时必须同时具备这个标记，以及与之完全吻合、通过校验的 JSON 快照。已经存在的快照或标记文件名绝不会被覆盖。标签（label）只能使用字母、数字、`.`、`_` 和 `-`。快照包含账户、余额、交易（含已回溯标记）和已用过的一次性序号，但绝不包含存储密码或 webhook 网址。对 MySQL 来说，它是通过实时连接读取数据；这仍然是一份逻辑快照，不是 `mysqldump`／`mariabackup` 那种原生或物理备份。

要把快照正式发布出来，文件系统需要支持安全的目录写入机制、不跟随符号链接的属性检查、常规文件检查，以及强制写入的文件通道。这个机制是应用层的生效标记协议，并不依赖系统底层的原子重命名或硬链接。如果文件系统不支持，或者标记／快照写到一半失败，指令会安全地失败、拒绝写入，而不会退而求其次用不安全的方式写。搬移快照时，请把配对的 `.json` 和 `.ready` 一起搬；只有 `.json` 不算一份已提交的备份。如果留下一个没有标记的残档，还原时也会被拒绝。

还原是破坏性操作，并且有严格的门槛：

```text
/aceeco restore <backup-id> confirm
```

- 仅限控制台执行；需要 `aceeconomy.admin` 加上 `aceeconomy.admin.restore`，而且要逐字输入 `confirm`。
- 只要还有任何玩家在线就会被拒绝；请先请所有人离开。
- 在动到正式数据之前，它会先校验快照，并为当前状态建立一份安全备份。如果这份安全备份失败，什么都不会还原。
- 成功后会回报旧状态的安全备份 ID，并清空排行榜缓存。让玩家回来之前必须重启；已经打开的会话和界面不会热刷新。

没有独立的 `/backup` 或 `/restore` 根指令；这些操作只作为 `/aceeco` 的管理子指令存在。

受管还原并不要求你在执行指令前另外手动停服或复制文件，但仍建议安排在维护时段进行。在线玩家门槛、执行前检查和还原前的安全备份都在保护这次操作；即使快照损坏或版本不兼容，也绝不能作为删除正式数据的理由。

## 安全控制：冻结与唯读

两级止血都不影响查询。冻结单个账户会拒绝所有触碰它的余额变更：Vault 存取、转账的转出与转入、支票出票与兑票、管理端的 `give`/`take`/`set`（没有例外）、触碰冻结账户的导入与回滚，以及正式与快照联集里带冻结账户的还原（整单拒绝，判定与发布在同一个独占窗口里，快照里没有正式世界的冻结账户也删不掉它）。全服唯读会拒绝所有账户的余额变更。查余额、查明细、排行榜、试运行预览、备份都不经过这道门。被拒绝的转账一分钱都不会扣，被拒绝的兑票也不会烧掉序号。一次确定没有暴露出可兑票据的失败出票，会凭单次有效的可信授权（序号、账户、货币、金额、用途）走免门禁的退款；未知、没扣过、已兑过、被篡改、重复、已花费、不确定、跨用途、以及没有绑定台账的证明一律拒绝，普通存入绝不能蹭这条路。用途在授权时就绑定（失败出票与不确定交接是两种用途），每次认领与重试都要连用途带四字段一起核对；跨用途的认领直接拒绝，不产生副作用，也不会吃掉正确用途的授权。授权只结算一次：已入账的记为已退款，没证明结果的记为不确定（保留、不再授权），只有确定没提交的失败才会用相同用途释放同一个授权给重试。票据到底有没有交到玩家手上无法确认时（地域回调抛出异常），绝不走上面那条一般退款：不确定交接专用的授权会把序号作废，并在同一笔存储交易内退款，一样免门禁，可兑票据和退款绝不会同时存在。

状态放在 `<plugin data folder>/security-control.json`，跟数据文件夹并列，绝不在经济快照里。状态与控制审计总是一起原子发布（临时文件加原子移动，再做落盘同步）；替换之前的失败两边都不生效。不支持原子移动的文件系统会直接拒绝发布，绝不静默走非原子替换。替换落地之后同步失败会采用新状态，绝不谎称什么都没生效。第一次启动没有这个文件会以可写状态打开。发布者写下的每个字段（format、version、globalReadonly、frozen、audits 里的 id、操作、操作者、原因、时间与目标）都必须存在、非空、类型精确且 UUID 为规范小写；缺字段、空值、类型写错、版本号为负或带小数、未知 format、坏 UUID 或重复 UUID、审计非法，都会跟损坏文件一样 fail-closed，只有未知的额外字段会忽略兼容。文件损坏、缺字段或读不出来就 fail-closed：所有余额变更都被拒绝，并给出固定的响亮诊断（绝不回显文件原文），读取路径绝不覆盖或删除这个文件。冻结、解冻、唯读三条变更在玩家查找之后走共用 IO 线程；地域线程不拿控制写锁也不做落盘同步，指令会立刻返回，真正的回复只在变更完成后走地域分发发一次。这个 IO 安排只覆盖控制指令：已通过 mutation permit 的普通同步金流，在控制写锁做落盘同步期间仍会等待。这是已接受的线性化代价；慢盘等待量测留给整合验证（真实 Folia/MySQL/重启尚未验证）。执行线程缺失或拒绝会给出明确的类型化拒绝，不改变任何状态。唯读开关关不掉读取失败，只能修文件再重启。`/aceeco reload` 不碰这份控制。普通备份里没有它，还原也绝不替换它：要备就停服后另外复制，或走受控的快照导出。降级到不认识这个文件的旧版本会失去保护，这是已知取舍，不会静默桥接。

每次被拒绝的余额变更动作都只在 `<plugin data folder>/security-control-attempts.jsonl` 留一条最小证据（操作、目标账户、固定拒绝分类、控制版本、可信操作者、时间）。多账户的拒绝也只留一条，写明被冻的目标（全服级拒绝则没有目标）。完整指令、网络身份、原始原因原文一律不存。追加串行走 IO 线程，绝不在地域线程上跑；追加失败会大声记日志，内存里的记录保留，拒绝照样成立。内存只保留最近 1024 条，文件台账每条都完整追加。控制审计和台账目前都没有删除和保留策略：只会一直增长，等管理员自己归档。这些记录只是只读证据，永远拼不回控制状态。

可信退款台账是单服内存：重启会 fail-closed 清空待授权（绝不双花）。退款证明不了的失败出票会带着它的票据（序号、玩家、金额、阶段）进入 pending 等人工对账，绝不盲目重试。

## 整合功能

Vault 和 PlaceholderAPI 都是可选插件。少了其中任何一个，经济核心依然能跑。Vault 使用配置里设定的默认货币；PlaceholderAPI 使用 `aceeco` 这个命名空间：

```text
%aceeco_balance%
%aceeco_balance_formatted%
%aceeco_balance_<currency>%
%aceeco_balance_<currency>_formatted%
```

Discord 通过 `discord.enabled` 和 `discord.webhook-url` 配置。真正的 webhook 只放在服务器本机。通知是异步、尽力而为的：通知出了问题，要和已经完成的交易分开处理。通知没到不代表钱没动，先查余额和交易记录。

## 停服、重启与重新开放

想停服或重启，请使用平常的服务管理方式，或服务器控制台指令：

```text
stop
```

请等待世界和插件的保存都完成。重启之后，先重做一遍每日开服检查，再让玩家回来。如果这次重启是因为上一次重新加载失败，请先还原最后一份确认正常的配置，免得服务器反复用同一份错误配置启动。

## 紧急回退

如果要回溯单笔已经记录的交易，请从控制台执行：

```text
/aceeco rollback <transaction-id>
```

这条指令仅限控制台，需要 `aceeconomy.admin` 加上 `aceeconomy.admin.rollback`，并且会明确回报每一种结果：成功时会列出回溯审计记录的 ID；已经回溯过的交易是安全的无操作；如果标记持久化失败，代表效果可能已经发生，却没有留下持久记录。重试之前，请先检查存储并人工核对。完整的结果对照表见[指令与权限](commands.zh-CN.md)。

回退指令已经接进正式的指令介面，也有自动化合约测试覆盖，但真实的线上验证还没做完：Folia/Bukkit 桥接的实机执行、真实的 MySQL 存储，以及用真实数据做的故障注入演练都还没跑。在这道发布门槛合上之前，请只在事先备好份的受控演练中使用它。

## 把问题交给支持人员

请使用[故障排除](troubleshooting.zh-CN.md)，并提供：最早出现的相关错误、版本号、当前存储类型、已经去掉敏感值的完整指令，以及事件发生的时间。数据文件、备份、密码、权杖和 webhook 网址都要保密。
