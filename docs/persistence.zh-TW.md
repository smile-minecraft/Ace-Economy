## 選擇儲存方式

AceEconomy 用同一套 v2 邏輯資料，但可以選擇不同的存放方式：JSON 檔案、SQLite 檔案，或透過 `storage.mysql.*` 設定的 MySQL 連網資料庫。JSON 與 SQLite 都放在插件資料夾裡。無論選哪一種，改變的只是資料的實體存放位置，不會改變[資料庫概念與升級](database.zh-TW.md)裡說明的帳戶與交易概念。

| 儲存方式 | 資料位置 | 適合情境 |
| --- | --- | --- |
| JSON | `<plugin-data>/data-v2.json` | 單一伺服器，想要一個便於攜帶的檔案。 |
| SQLite | `<plugin-data>/<storage.sqlite.path>` | 單一伺服器，想要一個本機 SQL 資料庫檔案。 |
| MySQL | `host:port/database` 所對應的資料庫。 | 已經有一套資料庫服務在運作的單一伺服器。 |
| MariaDB | 透過 `storage.type: mysql` 設定；沒有 `mariadb` 這個值。 | 使用 MySQL 相容連線方式的 MariaDB 服務的單一伺服器。 |

儲存方式會在啟動時選定。修改 `storage.type` 只會讓插件指向另一個存放位置，不會自動複製舊資料，也不會把兩個儲存合併在一起。

## 一份儲存只給一台伺服器

一份儲存只服務一台正在運作的伺服器。把兩台伺服器（或兩個插件實例）指向同一個 JSON 檔案、同一個 SQLite 檔案，或同一個 MySQL 資料庫，不在支援範圍內。

各後端的寫入協調只限於同一個執行中的實例。JSON 後端用實例內的鎖序列化寫入，再以原子替換發布；兩個寫入者共用同一個檔案時會靜默互相覆蓋，而每個實例各自沿用記憶體裡的視圖，餘額與交易紀錄可能在沒有任何錯誤的情況下分歧。SQL 後端同樣沒有跨實例的防護，併發寫入交錯提交時雙方都察覺不到。放在網路掛載上的 SQLite 檔案，還會疊加掛載本身的鎖定行為，插件對此不做任何驗證。

> **警告：**插件在啟動時不會診斷這種誤設。兩台伺服器指向同一份儲存時都會正常啟動；損壞要到後來才以遺失或矛盾的紀錄現形。請在維運上直接避免：一台伺服器，一份儲存。

多台伺服器請各自使用獨立的儲存（各自的檔案，或各自的 MySQL 資料庫）；伺服器之間搬移資料，只能走受管的 `/aceeco backup` 與 `/aceeco restore` 快照流程。多台伺服器共用一份即時儲存，需要獨立的鎖定與世代或防護機制設計，不屬於目前儲存後端的一部分。

## 鎖與世代的容量上限

實例內的鎖本身不存條目，只在同一台運作中的伺服器裡序列化工作。真正隨時間增長的是鎖旁邊的追蹤表，以及持久化的歷史紀錄。下面每張有界追蹤表共用同一個實測上限 `LockEpochCapacity.MAX_TRACKED_IDS`（10 萬個互不相同的 ID）。

| 增長的東西 | 隨什麼增長 | 上限 | 超過上限時 |
| --- | --- | --- | --- |
| 會話失效世代 | 累計載入過的互不相同 UUID | 10 萬 | 新 UUID 的載入直接失敗，錯誤為 `SessionError.CAPACITY_EXCEEDED`；已有會話不受影響。重啟伺服器即可重置追蹤。 |
| 餘額快取世代 | 累計快取過的互不相同擁有者 | 10 萬 | 新擁有者走無快取路徑（讀取直接落到儲存）；發布回傳 `false`。已有擁有者不受影響。 |
| 刷盤失敗診斷 | 有未確認刷盤失敗的互不相同 UUID | 10 萬 | 會話清理完成後，再記錄失敗會拋出 `SessionError.CAPACITY_EXCEEDED`。過期條目在下次登入或乾淨離開時刪掉。 |
| SQL 連線池 | 並發使用 SQL 的呼叫端 | `pool-size`（預設 10） | 借不到連線時先等待，再以明確的逾時失敗，絕不靜默。 |
| 64 位元世代計數器 | 失效次數 | 不設上限（有意為之） | 實務上不可能溢位：即使每秒失效 100 萬次，也有約 29.2 萬年的餘裕。 |

上限的依據：
- **量測範圍**：測試預先生成互不相同的 UUID 陣列，才記錄基準堆記憶體（`SessionTrackingCapacityMeasurementTest`）。實測的差值僅涵蓋 Map 條目結構與值物件（新的 `AtomicLong` 實例或共用的 `SessionError` 列舉參照），不包含 UUID 金鑰物件本身的堆記憶體占用。若將互不相同的金鑰物件（每個約 32 位元組）算進去，總堆記憶體占用會再增加。
- **測試 JVM 上的觀察值**（為實際執行的觀察數字，不同 JVM 版本與多次執行會有變動，並非固定保證或最壞情況上界；本節之 MB 均為十進位，1 MB = 1,000,000 位元組）：
  - **會話失效世代與餘額快取世代**（`UUID -> AtomicLong`）：10,000 筆時觀察到約 626 KB（每筆約 62.6 位元組）；滿額 100,000 筆時觀察到約 7.05 MB（每筆約 70.5 位元組）。
  - **刷盤失敗診斷**（`UUID -> SessionError`）：10,000 筆時觀察到約 386 KB（每筆約 38.6 位元組）；滿額 100,000 筆時觀察到約 4.87 MB（每筆約 48.7 位元組）。
  - **三張表同時滿額實測**（兩張世代表加一張刷盤診斷表同時填滿各 100,000 筆）：於測試 JVM 上直接實測，堆記憶體差值約 20.6 MB（三表合計每 key 約 206 位元組），填表耗時視機器與負載而定；本機觀察約 60 至 80 毫秒。
- **斷言實際保護的門檻**：測試保護的不是固定 MB 總量，而是每筆成本的上限門檻：
  - 世代持有者表：100,000 筆時嚴格保護在每筆 120 位元組以內（10,000 筆時為 150 位元組以內）。
  - 刷盤診斷表：100,000 筆時嚴格保護在每筆 80 位元組以內（10,000 筆時為 120 位元組以內）。
  - 三張表同時滿額：三表合計嚴格保護在每 key 320 位元組以內。
  只有成本漂移超過這些門檻時，自動化測試才會報錯。
- **完整會話工作集**：10,000 次被追蹤的會話載入（帳戶、快照與持有者條目合計）自動化測試實測裝得進 64 MB 堆記憶體內。
- **持久化已消耗 Nonce**：自動化測試實測第一筆消耗新增 61 個 JSON 字元，10,000 筆平均每筆精確為 61.9999 字元（約 62 字元）。

量測方式說明：於自動化容量測試套件（`SessionTrackingCapacityMeasurementTest`）中執行。測試預先生成互不相同的 UUID 陣列，並在紀錄前後執行多次暖機與垃圾回收（GC）穩定堆記憶體，由迴歸斷言保護每筆成本門檻。重啟會清掉全部三張追蹤表，這是安全的，因為重啟後沒有還在飛的載入或過期寫入。

持久化增長有意不設上限：已消耗的 nonce 與交易歷史永不刪除，刪 key 會破壞 first-writer-wins，刪歷史會銷毀稽核證據。請把檔案與資料表大小列入日常巡檢，伺服器之間搬資料只走受管的備份與還原流程。

沒有量測、也不做保證的項目：SQLite/MySQL 裡的單列儲存開銷、網路掛載上 SQLite 檔案的行為、硬體斷電能否存活、真實玩家執行緒下的堆記憶體行為、長時間執行的增長、真實 MySQL 列鎖下的並行交錯，以及用舊版程式讀取新資料。空候選（升級前備份）的遷移回退也沒有在實機上執行過，由自動化測試覆蓋。這些仍是待驗證的維運事項，不是本指南承諾的保證。

## JSON 檔案

當 `storage.type: json` 且目標檔案不存在時，插件會自動建立 `data-v2.json`。每次資料異動時，後端均遵循寫時複製（Copy-on-Write）原則：
1. **暫存寫入與強制落盤：** 先於正式檔案旁建立暫存檔，寫入完整快照後執行 `fsync` 強制刷盤。
2. **原子替換（Atomic Move）：** 透過檔案系統的原子移動替換目標檔案，並同步目錄元數據。正式檔案永遠保持完整快照狀態，絕不會出現寫入一半的損毀內容。
3. **錯誤與失敗復原：** 寫入中斷時會嘗試清理暫存檔；底層檔案系統若不支援原子替換則直接拋錯，絕不降級為非原子寫入。若替換已完成但後續落盤確認失敗，系統會將狀態標記為已提交，並立即暫停後續寫入以防數據分歧，須待重啟確認檔案。

*注意：本機制之自動化測試僅驗證 I/O 異常，未模擬底層硬體斷電情境。*

JSON 模型包含 schema 版本、帶餘額的帳戶與交易紀錄。金額以十進位字串保存，不會因為浮點格式轉換而改變儲存下來的數值。

### 安全操作檔案

- 複製、替換或搬移 `data-v2.json` 之前，必須先停止伺服器。
- 除非插件改用了其他受支援的儲存方式，否則檔案必須留在插件資料夾內。
- 保留多份帶日期的備份，並記錄每份備份當時對應的設定。
- 不要手動修改餘額或交易紀錄。

## SQLite 檔案

SQLite 使用 `storage.sqlite.path` 指定的路徑，該路徑在插件資料夾下解析，預設值是 `data-v2.sqlite`。如果解析出來的路徑跑出了這個資料夾（包括用 `..` 往上跳，或使用指向其他根目錄的絕對路徑），解析器會直接拒絕。

SQLite 資料庫在初始化時會建立 v2 資料表。建立 schema 與寫入一批交易紀錄都包在同一個資料庫交易裡。重啟時，插件會重新開啟同一個檔案並初始化既有的 schema，不會重複插入版本列。

做檔案備份時，先停止伺服器，複製 SQLite 檔案，再把副本放到正式插件資料夾之外。還原時則是停止伺服器、把選定的檔案放回設定路徑，然後重新啟動伺服器。

## MySQL 與 MariaDB

`mysql` 資料庫會依據 YAML 裡的值拼出 `jdbc:mysql://<host>:<port>/<database>`，再把憑證與連線池參數交給 HikariCP，並在這個連線上開啟一個 SQL 資料庫。插件包裡已經包含了所需的 JDBC 驅動，本文所說的伺服器部署不需要你另外放一個驅動檔案。

```yaml
storage:
  type: mysql
  mysql:
    host: "db.example.invalid"
    port: 3306
    database: "aceeconomy"
    username: "<database-user>"
    password: "<set-locally>"
    pool-size: 10
    max-lifetime: 1800000
```

`pool-size` 必須是正數，用來限制連線池的最大連線數。`max-lifetime` 也必須是正數，單位是毫秒。這兩個值要放在 `storage.mysql` 之下，而不是作為全域的 `storage` 鍵。

使用 MariaDB 時，同樣保持 `type: mysql`，填入 MariaDB 的主機、連接埠、資料庫、帳號與密碼即可。設定裡沒有獨立的 `mariadb` 分支。

## 日常運作的安全邊界

### 寫入與交易

- 單筆交易紀錄要嘛被寫入，要嘛被拒絕；重複的交易 ID 不會被悄悄覆寫。
- 一批紀錄會作為一個資料庫交易提交。其中一筆失敗時，整批都會回滾。
- 把一筆既有交易標記為「已撤銷」可以重複執行，是安全的。
- 程序重啟會重新開啟同一個儲存，不會改選其他儲存方式，也不會遷移資料。

### 受管備份

伺服器運作中，使用下面這條標準指令建立一份邏輯快照：

```text
/aceeco backup [label]
```

這條指令只會在插件控制的 `<plugin data folder>/backups` 目錄下，寫出一份不含任何密碼的 v2 JSON 快照。附加的標籤（label）只能使用安全的檔名字元。寫入時，系統會先以「不存在才建立」的方式生成 `<backup-id>.json`，把完整快照寫進去，再以同樣方式生成 `<backup-id>.ready`。這個 `.ready` 檔案裡含有 SHA-256 校驗和，是整份快照「正式生效」的標記：還原時必須同時具備 `.ready` 檔案，以及與之完全吻合、通過校驗的 `.json` 快照。已經存在的快照或標記檔案絕不會被覆蓋。快照包含邏輯帳戶、餘額、交易、已撤銷標記、已用過的一次性序號與託管出票進度，但不包含資料庫密碼或 webhook 網址。搬移快照時，請把配對的 `.json` 與 `.ready` 一起搬；只有 `.json` 不算一份已提交的備份。

沒有獨立的 `/backup` 或 `/restore` 根指令；這些操作只以 `/aceeco` 的管理子指令存在。指令細節與權限見[指令與權限](commands.zh-TW.md)。

## 還原流程

> **警告：** 還原是破壞性操作。即使快照損壞或不相容，也絕不能當成刪除正式資料的理由。

必須從伺服器主控台執行下面這條精確指令：

```text
/aceeco restore <backup-id> confirm
```

這條指令需要 `aceeconomy.admin` 與 `aceeconomy.admin.restore` 兩項權限，只要還有任何玩家在線就會拒絕執行，而且只接受小寫的 `confirm`。在動到正式資料之前，系統會先做一輪唯讀預檢：檢查 JSON 結構、schema 版本、帳戶與交易紀錄、重複的交易 ID、金額與時間戳，以及和目前貨幣設定的相容性。預檢通過後，它會先為目前狀態建立一份安全備份；如果這份安全備份失敗，還原就會中止，正式狀態原封不動。

託管出票護欄接著比對線上與候選快照的出票紀錄：沒有出票進度的候選（升級前寫下的備份）只在線上沒有可兌票時才能整份取代——尚未扣款、尚未交件、已兌換或已作廢且無票的線上紀錄才能回退，這是正式支援的遷移回退路徑。線上已有交件、可能已交件、已退款停票或無法判定的紀錄會整單拒絕，避免餘額回復後背包裡的支票仍可兌換或再度可兌換。

已交件或可能已交件的紀錄，只有在真正完成兌換並標記為已兌換之後，才能解除阻擋。已退款停票與隔離中（無法判定）的紀錄目前沒有正式的解除流程，需要管理員評估後另行處理（例如依事故處置程序），光是處理掉手上的實體票並不保證能回退。若兌換已入帳但標記失敗（會留下響亮診斷），紀錄會停在已交件並繼續拒絕回退。其他情況下，每筆線上託管紀錄必須在候選中原樣存在；候選中新出現且帶有扣款證據的紀錄，必須在同一份快照裡附帶權威扣款。

一般一次性序號不在這層護欄範圍內。還原會把餘額與一般序號一起回退，而實體支票放在玩家背包、不在經濟快照裡，所以護欄不保證還原後的序號永不重複使用。它只保證：還原不會讓已交件、可能已交件或已退款停票的託管票在餘額回復後仍可兌換或再度可兌換，還原也不會憑空生出退款。退款或作廢只會讓票號在帳上停用，實體票仍可能留在玩家手上並被再次送入，所以這類紀錄和已交件紀錄一樣會擋下升級前備份的回退。

預檢與安全備份都通過後，JSON 還原會透過安全的目錄寫入機制讀取已經提交完成的標記檔案與快照配對；這個標記機制是應用層的生效確認，並不依賴系統底層的原子重新命名或硬連結。SQLite 與 MySQL 的還原則作為一個 JDBC 交易執行。如果資料庫在還原時出錯，系統會如實報告失敗，而不會謊稱正式資料沒有變動。還原成功後，排行榜快取會被清空，但玩家的會話與介面不會熱刷新；讓玩家回來之前，請先重啟伺服器。

交件持久化窗口（已知限制）：託管支票先在地域執行緒放進玩家背包，之後才在 IO 執行緒寫下交件註記。啟動恢復會退還仍停在開始交件的紀錄，但已讀為交件完成的紀錄永不退款。所以兩種先後順序都很關鍵：在背包交接之後、交件註記落地之前停掉程序，重啟後會退款（若世界存檔已先寫下票據，票也會留下）；在交件註記落地之後、世界與玩家資料存檔之前停掉程序，玩家付了錢卻既沒有票也拿不到退款。經濟快照與世界存檔是兩套各自的時間點，中間沒有共同的原子邊界——以上是按目前程式順序推得的結論，尚未在正式伺服器上驗證。同次演練的實機觀察：提領後斷線，出票維持 `DELIVERED`、餘額不變，也沒有幽靈交易；重新連上後支票仍在玩家背包，兌換後正確變為 `REDEEMED`。指令送出後立刻被踢線時，指令根本沒有生效，也沒有留下半套狀態。上面那種「付了錢卻既沒有票也拿不到退款」的順序，仍未在實機上驗證。請正常停服，並等世界與插件存檔完成。

## 邏輯層面的儲存邊界

JSON、SQLite 與 MySQL 之間的邏輯備份與還原，共用同一套 v2 JSON 模型。因此可以做 JSON→JSON、SQLite→JSON→SQLite，以及相應的 MySQL 邏輯路徑。但這**不是** MySQL 伺服器原生的匯出：它不能取代 `mysqldump`、`mariadb-dump`，也不能取代資料庫管理員負責的實體／災難復原流程。

自動化來回轉換測試已經確認了 JSON→JSON 與 SQLite→JSON→SQLite，涵蓋帳戶、餘額、交易、已撤銷標記、已用過的一次性序號與託管出票進度，以及還原失敗時的資料庫回滾。2026-10-13 的實機驗證補上了 MySQL 連線本身（餘額經 MySQL 讀寫，本機檔案完全沒動）、受管備份的建立，以及 Folia 配 MySQL 下還原護欄的拒絕路徑。完整成功的還原交換與原生／實體災難復原，仍屬於待做的操作驗證項目，本文不會把它們說成已經確認的結果。

## 實機驗證

2026-10-13 用目前原始碼在 Folia 26.2 build 7 上做了一輪實機演練，儲存使用專用 MySQL 資料庫，共 7 張表（`ace_v2_accounts`、`ace_v2_balances`、`ace_v2_transactions`、`ace_v2_nonces`、`ace_v2_issuances`、`ace_v2_operation_audits`、`ace_v2_schema`）。確認成立的結果：

- **MySQL 真的是後端。** `/aceeco take` 扣款後 MySQL 餘額同步變化，`/money balance` 回應的值等於 MySQL 的值。本機 `data-v2.json` 與 `data-v2.sqlite` 的修改時間完全沒動，確認本輪沒有寫入本機檔案。
- **乾淨重啟什麼都留著。** 正常停服再啟動後，資料表筆數、五個帳戶餘額、出票狀態、已消費票號、交易統計完全一致。
- **還原護欄照設計拒絕。** 出票維持已交件、沒有玩家在線時，主控台拿舊快照還原被拒，因為線上出票進度在候選中缺失；出票筆數、餘額、交易筆數事後完全不變，還原前先寫好了 pre-restore 安全備份。完整成功的還原交換不在本輪範圍內。
- **不同區域並行仍然成對。** 四個玩家分散到四個相距約一萬格的象限後並行轉帳：12 筆轉出（132.00）對上 12 筆轉入（132.00），餘額變化與金額一致。
- **台帳自洽。** 每個帳戶每個幣別的餘額，都等於其最後一筆交易的 `balance_after`；`reason` 欄位長度為 512。
- **回滾可逆轉一筆存入。**一筆 77.00 的存入讓餘額從 1440.00 變為 1517.00，並在 `ace_v2_transactions` 確認為一筆 `DEPOSIT` 紀錄（`balance_before`／`balance_after` 相符）；依交易 ID 回滾後，餘額從 1517.00 回到 1440.00。

同次演練中玩家看得到的結果（支票、Java 版介面、背包滿的拒絕、斷線行為、匯入）寫在[伺服器維運](operations.zh-TW.md#實機驗證)。

SQLite 與 JSON 兩輪在同一天、同一個版本上進行，切換 `storage.type` 之前都先停服並備份前一個儲存：

- **SQLite 輪（`data-v2.sqlite`）。**金流與 MySQL 一致：從 1000.00 出發，`/aceeco give`（+100）、`take`（-30）、`set`（設為 500.00）都生效，`/money balance` 回報 500.00，機器人轉帳的一筆 20.00 正確移動。回滾那筆 100.00 的存入，餘額從 430.00 變為 330.00。`/withdraw cash 100` 讓餘額從 480.00 變為 380.00 且支票在背包，右鍵兌換後從 380.00 回到 480.00。`/aceeco import cmi … apply confirm` 先建立 pre-import 安全備份，再套用 1 筆、0 筆跳過、0 筆失敗（測試餘額從 1000.00 變為 999.00）。故障路徑與 MySQL 一致：凍結帳號的 `take` 被拒（`ACELIB-CMD-ACCOUNT-FROZEN`），全服唯讀的 `give` 被拒（`ACELIB-CMD-GLOBAL-READ-ONLY`），有 `DELIVERED` 出票未結時還原被拒（`Restore refused: live issuance progress for a nonce is missing from the candidate snapshot`），拒絕後餘額不變。正常停服後直接讀檔檢查（md5 `08c5edd8…`）確認七張表、五個餘額（430／1020／999／1000／1000）、帶原因的交易與兩筆出票；重啟後 `/money balance` 逐一查詢全部五個帳號，回報值與停服時直接讀檔的結果一致。
- **JSON 輪（`data-v2.json`）。**金流與 MySQL 一致：從 999.00 出發，`give`（+100）、`take`（-30）、`set`（設為 500.00）都生效，機器人轉帳讓一方從 999.00 變為 979.00，對方從 1000.00 變為 1020.00。回滾那筆 100.00 的存入，餘額從 500.00 變為 400.00。提領 100 讓餘額從 979.00 變為 879.00 且支票在背包，右鍵兌換後從 879.00 回到 979.00。匯入預演回報 1 筆可套用、0 筆跳過且沒有寫入；`apply confirm` 先建立 pre-import 安全備份，再套用 1 筆、0 筆跳過、0 筆失敗。凍結、唯讀、還原護欄的拒絕行為與 MySQL／SQLite 相同，拒絕後資料不變。正常停服後直接讀檔檢查（md5 `3c7326f0…`）確認 `accounts`／`transactions`／`nonces`／`issuances`／`schemaVersion` 區段，五個測試帳號餘額為 500.00／849.00／999.00／1000.00／1000.00；重啟後 `/money balance` 確認其中三個帳號，另兩個以停服時直接讀檔的結果為準。稍後在 JSON 設定下再次查詢全部五個帳號，五個值都與資料檔一致。

## 啟動失敗時

- 確認 `storage.type` 是三個可接受值之一。
- 使用 SQLite 時，確認 `storage.sqlite.path` 是一個包含 `path` 的 YAML 對應表，且解析後的路徑仍落在插件資料夾內。
- 使用 MySQL 或 MariaDB 時，檢查主機、連接埠、資料庫、帳號、密碼與網路連通性。
- schema 版本不相容，不是改個儲存方式就能修好的。請先備份，再依照[資料庫概念與升級](database.zh-TW.md)裡的 v2 升級說明處理。
