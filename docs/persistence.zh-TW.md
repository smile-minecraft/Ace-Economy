## 選擇後端

AceEconomy 會透過 JSON 檔案或 SQL 後端保存同一套 v2 邏輯資料。JSON 與 SQLite 都放在插件資料夾裡；MySQL 則是透過 `storage.mysql.*` 設定的連網資料庫。無論選哪一種，改變的只是資料的實體存放位置，不會改變[資料庫概念與升級](database.zh-TW.md)裡說明的帳戶與交易概念。

| 後端 | 資料位置 | 適合情境 |
| --- | --- | --- |
| JSON | `<plugin-data>/data-v2.json` | 單一伺服器，想要一個便於攜帶的檔案。 |
| SQLite | `<plugin-data>/<storage.sqlite.path>` | 單一伺服器，想要一個本機 SQL 資料庫檔案。 |
| MySQL | `host:port/database` 所對應的資料庫。 | 已經有一套資料庫服務在運作。 |
| MariaDB | 透過 `storage.type: mysql` 設定；沒有 `mariadb` 這個值。 | 使用 MySQL 相容連線方式的 MariaDB 服務。 |

後端會在啟動時選定。修改 `storage.type` 只會讓插件改指另一個儲存位置，不會自動複製舊資料，也不會把兩個儲存合併在一起。

## JSON 檔案

當 `storage.type: json` 且資料夾裡沒有對應檔案時，插件會建立 `data-v2.json`。每次資料變動，插件都會先寫入一個暫存檔，再整體替換成正式檔案，因此落盤的是一份完整的檔案，而不是寫到一半的殘破文件。

JSON 模型包含 schema 版本、帶餘額的帳戶與交易紀錄。金額以十進位字串保存，不會因為浮點格式轉換而改變儲存下來的數值。

### 安全操作檔案

- 複製、替換或搬移 `data-v2.json` 之前，必須先停止伺服器。
- 除非插件改用了其他受支援的後端，否則檔案必須留在插件資料夾內。
- 保留多份帶日期的備份，並記錄每份備份當時對應的設定。
- 不要手動修改餘額或交易紀錄。

## SQLite 檔案

SQLite 使用 `storage.sqlite.path` 指定的路徑，該路徑在插件資料夾下解析，預設值是 `data-v2.sqlite`。如果解析出來的路徑跑出了這個資料夾（包括用 `..` 往上跳，或使用指向其他根目錄的絕對路徑），解析器會直接拒絕。

SQL 後端在初始化時會建立 v2 資料表。建立 schema 與寫入一批交易紀錄都包在同一個資料庫交易裡。重啟時，插件會重新開啟同一個檔案並初始化既有的 schema，不會重複插入版本列。

做檔案備份時，先停止伺服器，複製 SQLite 檔案，再把副本放到正式插件資料夾之外。還原時則是停止伺服器、把選定的檔案放回設定路徑，然後重新啟動伺服器。

## MySQL 與 MariaDB

`mysql` 後端會依據 YAML 裡的值拼出 `jdbc:mysql://<host>:<port>/<database>`，再把憑證與連線池參數交給 HikariCP，並在這個連線上開啟一個 SQL 後端。插件包裡已經包含了所需的 JDBC 驅動，本文所說的伺服器部署不需要你另外放一個驅動檔案。

```yaml
storage:
  type: mysql
  mysql:
    host: "db.example.invalid"
    port: 3306
    database: "aceeconomy"
    username: "<database-user>"
    password: "<set-locally>"
    pool-size: 10
    max-lifetime: 1800000
```

`pool-size` 必須是正數，用來限制連線池的最大連線數。`max-lifetime` 也必須是正數，單位是毫秒。這兩個值要放在 `storage.mysql` 之下，而不是作為全域的 `storage` 鍵。

使用 MariaDB 時，同樣保持 `type: mysql`，填入 MariaDB 的主機、連接埠、資料庫、帳號與密碼即可。設定裡沒有獨立的 `mariadb` 分支。

## 日常運作的安全邊界

### 寫入與交易

- 單筆交易紀錄要嘛被寫入，要嘛被拒絕；重複的交易 ID 不會被悄悄覆寫。
- 一批紀錄會作為一個資料庫交易提交。其中一筆失敗時，整批都會回滾。
- 把一筆既有交易標記為「已撤銷」可以重複執行，是安全的。
- 程序重啟會重新開啟同一個儲存，不會改選其他後端，也不會遷移資料。

### 受管備份

伺服器運作中，使用下面這條標準指令建立一份邏輯快照：

```text
/aceeco backup [label]
```

這條指令只會在插件控制的 `<plugin data folder>/backups` 目錄下，寫出一份不含任何密碼的 v2 JSON 快照。附加的標籤（label）只能使用安全的檔名字元。寫入時，系統會先以「不存在才建立」的方式生成 `<backup-id>.json`，把完整快照寫進去，再以同樣方式生成 `<backup-id>.ready`。這個 `.ready` 檔案裡含有 SHA-256 校驗和，是整份快照「正式生效」的標記：還原時必須同時具備 `.ready` 檔案，以及與之完全吻合、通過校驗的 `.json` 快照。已經存在的快照或標記檔案絕不會被覆蓋。快照包含邏輯帳戶、餘額、交易、已撤銷標記與已用過的一次性序號，但不包含資料庫密碼或 webhook 網址。搬移快照時，請把配對的 `.json` 與 `.ready` 一起搬；只有 `.json` 不算一份已提交的備份。

沒有獨立的 `/backup` 或 `/restore` 根指令；這些操作只以 `/aceeco` 的管理子指令存在。指令細節與權限見[指令與權限](commands.zh-TW.md)。

## 還原流程

> **警告：** 還原是破壞性操作。即使快照損壞或不相容，也絕不能當成刪除正式資料的理由。

必須從伺服器主控台執行下面這條精確指令：

```text
/aceeco restore <backup-id> confirm
```

這條指令需要 `aceeconomy.admin` 與 `aceeconomy.admin.restore` 兩項權限，只要還有任何玩家在線就會拒絕執行，而且只接受小寫的 `confirm`。在動到正式資料之前，系統會先做一輪唯讀預檢：檢查 JSON 結構、schema 版本、帳戶與交易紀錄、重複的交易 ID、金額與時間戳，以及和目前貨幣設定的相容性。預檢通過後，它會先為目前狀態建立一份安全備份；如果這份安全備份失敗，還原就會中止，正式狀態原封不動。

預檢與安全備份都通過後，JSON 還原會透過安全的目錄寫入機制讀取已經提交完成的標記檔案與快照配對；這個標記機制是應用層的生效確認，並不依賴系統底層的原子重新命名或硬連結。SQLite 與 MySQL 的還原則作為一個 JDBC 交易執行。如果後端出錯，系統會如實報告失敗，而不會謊稱正式資料沒有變動。還原成功後，排行榜快取會被清空，但玩家的會話與介面不會熱刷新；讓玩家回來之前，請先重啟伺服器。

## 邏輯層面的後端邊界

JSON、SQLite 與 MySQL 之間的邏輯備份與還原，共用同一套 v2 JSON 模型。因此可以做 JSON→JSON、SQLite→JSON→SQLite，以及相應的 MySQL 邏輯路徑。但這**不是** MySQL 伺服器原生的匯出：它不能取代 `mysqldump`、`mariadb-dump`，也不能取代資料庫管理員負責的實體／災難復原流程。

自動化來回轉換測試已經確認了 JSON→JSON 與 SQLite→JSON→SQLite，涵蓋帳戶、餘額、交易、已撤銷標記、已用過的一次性序號，以及還原失敗時的後端回滾。不過，目前還沒有完成真實的 MySQL 連線驗證，也沒有完成真實的 Folia 備份／還原驗證；這些仍屬於待做的操作驗證項目，本文不會把它們說成已經確認的結果。

## 啟動失敗時

- 確認 `storage.type` 是三個可接受值之一。
- 使用 SQLite 時，確認 `storage.sqlite.path` 是一個包含 `path` 的 YAML 對應表，且解析後的路徑仍落在插件資料夾內。
- 使用 MySQL 或 MariaDB 時，檢查主機、連接埠、資料庫、帳號、密碼與網路連通性。
- schema 版本不相容，不是改個後端名稱就能修好的。請先備份，再依照[資料庫概念與升級](database.zh-TW.md)裡的 v2 升級說明處理。
