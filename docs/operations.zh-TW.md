## 每次開服檢查

想確認伺服器可以接人，先看兩件事。正常啟動或重啟之後，在伺服器主控台確認出現了 `AceEconomy v2.2.0` 與 `AceLib v1.2.1`，並且只載入了一個 AceLib 版本。接著用一個測試帳號執行 `/money balance`，必要時再執行 `/baltop top`。

如果伺服器還沒準備好，不要對玩家開放。保留最早出現的那條 AceEconomy、AceLib 或儲存錯誤，然後依照[故障排除](troubleshooting.zh-TW.md)處理。

## 選擇與確認儲存方式

想知道資料存在哪裡，看 `storage.type` 就好，v2 後端由它決定：

| 值 | 位置 | 適用情境 |
| --- | --- | --- |
| `json` | `plugins/AceEconomy/data-v2.json` | 單一伺服器，使用本機檔案 |
| `sqlite` | 插件資料夾下的 `storage.sqlite.path` | 單一伺服器，使用 SQLite 資料庫 |
| `mysql` | `storage.mysql.*` | 使用受管理的 MySQL 或 MariaDB 服務的單一伺服器 |

SQLite 的路徑必須留在 `plugins/AceEconomy/` 之內。MySQL 的 `pool-size` 與 `max-lifetime` 必須放在 `storage.mysql` 之下，密碼不要寫進共用文件。

所有受支援的後端都使用同一套 v2 帳戶與交易模型。選錯後端多半開機就會報錯，做法見[故障排除](troubleshooting.zh-TW.md)。

一份儲存只服務一台正在運作的伺服器。不要把兩台伺服器指向同一個 JSON 檔案、SQLite 檔案或 MySQL 資料庫：這種接法不在支援範圍內，而且可能在沒有報錯的情況下分歧。詳見[持久化、備份與還原](persistence.zh-TW.md#一份儲存只給一台伺服器)。

## 安全地修改設定

想改設定又不想把服弄壞，照這套順序做。只有在你平時的變更流程能保護檔案不被寫壞時，才在伺服器運作中編輯 `plugins/AceEconomy/config.yml`。修改前先複製一份，保留 `version: "2.0"`，並在套用前確認 YAML 結構正確。

普通的設定或語言變更，請從主控台執行：

```text
/aceeco reload
```

成功時會回顯 `AceEconomy reloaded`。如果新的設定或語言檔載入不了，插件會保留最後一份有效的記憶體快照，不會用半成品設定頂替。但如果你改動了 `storage.type`、SQLite 路徑、MySQL 連線值、插件 JAR、AceLib 或選用插件，就必須完整停服再啟動，只做重新載入不夠。

重新載入是一整筆交易：設定、語言、貨幣、銀行介面四組候選會先各自驗證，全部通過才一起換上。任一組失敗就什麼都不換，伺服器沿用舊設定繼續跑。

貨幣修改會在交換前先分類：

| 變更 | 重新載入怎麼做 | 為什麼 |
| --- | --- | --- |
| 沒變 | 重新載入成功，什麼都不換。 | 沒有東西要套用。 |
| 只改 `name` 或 `symbol` | 直接熱套用，新顯示文字立刻全服生效。 | 顯示文字不影響已存金額、小數位數與預設貨幣。 |
| 新增貨幣 | 重新載入拒絕並告知新增的 ID，伺服器沿用舊組合。請重啟才會生效。 | 既有帳戶需要批次初始化並支援回溯，目前沒有儲存後端能做到。 |
| 移除貨幣，或改 `scale`、改 `default` | 重新載入拒絕並告知受影響的 ID，伺服器沿用舊組合。請重啟才會生效。 | 這些變更會讓已存餘額被誤讀或變成孤兒。 |
| 候選區塊格式無效 | 重新載入拒絕並告知解析原因，什麼都不換。 | 讀不懂的候選設定絕不能取代線上登錄表。 |

有三個設定只能重啟，不會被重新載入套用。`settings.main-command-alias`、`storage.type`、`leaderboard.enabled` 如果和運作中的值不同，重新載入照樣成功，但回報會多一條點名的重啟提醒；線上值維持不動，下次完整重啟才會換。

回報會告訴你發生了什麼事。失敗時顯示拒絕理由，例如哪個貨幣 ID 被新增、哪個小數位數被改，讓你知道該修檔案還是排重啟。成功時附加備註：哪些已熱套用（顯示文字、版面、設定與語言），哪些還要重啟。

成功的重新載入會用新版面把已開啟的銀行介面原地重建並重開，不讓任何點擊卡在新舊規則之間；玩家不用重開 `/bank`。重建或重開失敗的介面才會關閉並告知玩家，關閉與告知皆為 best-effort。跟重新載入撞期的開啟會等交換完成，不管排在交換前後，建出來的都是當前版面。這是正常現象，不是東西壞掉。

同一次重新載入也會清空整個同步餘額快取。這是預期的接受行為，不是 bug，餘額不會真的不見：Vault 讀取絕不阻塞等待儲存，所以在下一次已持久化的讀取或成功寫入重新填入之前，餘額查詢會回到安全預設值 `0.0`。不會在呼叫執行緒上同步回填，因為那會把快取原本要避開的阻塞 I/O 帶回來。看到短暫的 0 先等一次正常讀寫，不用急著還原或重啟。

不要把 Bukkit 的 `/reload` 當成維護或升級的捷徑。

## 日常指令

想檢查運作中的伺服器，可以用這些格式：

```text
/money balance [player] [currency]
/pay send <player> <amount> [currency]
/withdraw cash <amount> [currency]
/baltop top [currency]
/bank open
/aceeco give <player> <amount> [currency]
/aceeco take <player> <amount> [currency]
/aceeco set <player> <amount> [currency]
```

請用一個測試帳號做小額、可回復的檢查，不要直接改動真實玩家的餘額。管理員調整餘額時，請記到伺服器平時的管理紀錄裡。指令打錯就對照[指令與權限](commands.zh-TW.md)的錯誤表。

## 備份與還原

受管的邏輯快照與手動的災難復原副本是兩套不同的流程，不要把其中一種的說明當成另一種來用。

### 手動檔案與資料庫災難復原

想自己留一份檔案級副本保命，先停服再動手。直接複製 JSON 或 SQLite 資料檔之前，必須先停服。手動副本要放在正式插件資料夾之外，檔名帶上日期與用途，也不要覆寫唯一一份確認正常的副本。這屬於檔案級的災難復原副本，不是受管的 `/aceeco backup` 指令。

MySQL 或 MariaDB 的原生／實體備份，請按資料庫管理員平時的備份流程來做，並和對應的伺服器設定備份一起保存。原生或實體的資料庫備份不等於受管的 v2 邏輯快照。目前本文還沒有驗證過真實的 MySQL/Folia 組合與災難復原流程；在正式依賴之前，請先在一次受控演練中確認可行。

### 受管指令

想在不停服的情況下留一份可還原的紀錄，主控台與獲得授權的管理員可以這樣做：

```text
/aceeco backup [label]
```

這條指令在伺服器運作中就能執行。它會在插件控制的 `<plugin data folder>/backups/` 目錄下，寫出一份不含任何憑證的 v2 JSON 邏輯快照。寫入時，系統會先以「不存在才建立」的方式生成 `<backup-id>.json`，把完整內容寫進去，再以同樣方式生成 `<backup-id>.ready`。這個 `.ready` 檔案裡含有 SHA-256 校驗和，是整份快照「正式生效」的標記；還原時必須同時具備這個標記，以及與之完全吻合、通過校驗的 JSON 快照。已經存在的快照或標記檔名絕不會被覆蓋。標籤（label）只能使用字母、數字、`.`、`_` 與 `-`。快照包含帳戶、餘額、交易（含已回溯標記）、已用過的一次性序號與託管出票進度，但絕不包含儲存密碼或 webhook 網址。對 MySQL 來說，它是透過即時連線讀取資料；這仍然是一份邏輯快照，不是 `mysqldump`／`mariabackup` 那種原生或實體備份。

要把快照正式發布出來，檔案系統需要支援安全的目錄寫入機制、不跟隨符號連結的屬性檢查、常規檔案檢查，以及強制寫入的檔案通道。這個機制是應用層的生效標記協定，並不依賴系統底層的原子重新命名或硬連結。如果檔案系統不支援，或者標記／快照寫到一半失敗，指令會安全地失敗、拒絕寫入，而不會退而求其次用不安全的方式寫。搬移快照時，請把配對的 `.json` 與 `.ready` 一起搬；只有 `.json` 不算一份已提交的備份。如果留下一個沒有標記的殘檔，還原時也會被拒絕。

還原是破壞性操作，並且有嚴格的門檻：

```text
/aceeco restore <backup-id> confirm
```

- 僅限主控台執行；需要 `aceeconomy.admin` 加上 `aceeconomy.admin.restore`，而且要逐字輸入 `confirm`。
- 只要還有任何玩家在線就會被拒絕；請先請所有人離開。
- 在動到正式資料之前，它會先校驗快照，並為目前狀態建立一份安全備份。如果這份安全備份失敗，什麼都不會還原。
- 託管出票護欄接著要求每筆線上託管紀錄在候選中原樣存在。升級前、沒有出票進度區段的候選，只有在線上沒有可兌票時才能整份取代（包含尚未扣款、尚未交件、已兌換或已作廢且無票的線上紀錄）。線上已有交件、可能已交件、已退款停票或無法判定的紀錄時會整單拒絕，避免餘額回復後背包裡的支票仍可兌換或再度可兌換。
- 已交件或可能已交件的紀錄，只有在真正完成兌換並標記為已兌換之後，才能解除阻擋。已退款停票與隔離中（無法判定）的紀錄目前沒有正式的解除流程，需要管理員評估後另行處理（例如依事故處置程序），光是處理掉手上的實體票並不保證能回退。若兌換已入帳但標記失敗（會留下響亮診斷），紀錄會停在已交件並繼續拒絕回退。候選中新出現且帶有扣款證據的紀錄，必須在同一份快照裡附帶權威扣款。一般序號不在這層護欄範圍內。
- 這層護欄不保證序號永不重複使用：還原會把餘額與一般序號一起回退，而實體支票放在玩家背包、不在經濟快照裡。護欄只保證兩件事：還原不會讓已交件、可能已交件或已退款停票的託管票在餘額回復後仍可兌換或再度可兌換，還原也不會憑空生出退款。退款或作廢只會讓票號在帳上停用，實體票仍可能留在玩家手上並被再次送入，所以這類紀錄和已交件紀錄一樣會擋下升級前備份的回退。在安全狀態下還原升級前的備份，才會連同出票進度一起取代，之後不會再依被取代的紀錄退款。
- 已知的交件窗口：票據先進入背包，交件註記才落地。若在註記落地之後、世界存檔之前停掉程序，紀錄已是終止的交件狀態（永不退款），票卻沒了。請正常停服，並等世界與插件存檔完成。
- 啟動恢復完成之前，新的託管出票與託管兌票會被擋下並留下響亮診斷；查詢與舊版票據不受影響。
- 成功後會回報舊狀態的安全備份 ID，並清空排行榜快取。讓玩家回來之前必須重啟；已經打開的會話與介面不會熱刷新。

沒有獨立的 `/backup` 或 `/restore` 根指令；這些操作只以 `/aceeco` 的管理子指令存在。

受管還原並不要求你在執行指令前另外手動停服或複製檔案，但仍建議安排在維運時段進行。在線玩家門檻、執行前檢查與還原前的安全備份都在保護這次操作；即使快照損壞或版本不相容，也絕不能當成刪除正式資料的理由。

## 安全控制：凍結與唯讀

兩級止血都不影響查詢。凍結單一帳號會拒絕所有碰到它的餘額變更：Vault 存取、轉帳的轉出與轉入、支票出票與兌票、管理端的 `give`／`take`／`set`（沒有例外）、碰到凍結帳號的匯入與回滾，以及正式與快照聯集裡帶凍結帳號的還原（整單拒絕，判定與發布在同一個獨佔窗口裡，快照裡沒有正式世界的凍結帳號也刪不掉它）。全服唯讀會拒絕所有帳號的餘額變更。查餘額、查明細、排行榜、試運轉預覽、備份都不經過這道門。被拒絕的轉帳一分錢都不會扣，被拒絕的兌票也不會燒掉序號。一次確定沒有暴露出可兌票據的失敗出票，會憑單次有效的可信授權（序號、帳號、貨幣、金額、用途）走免門禁的退款；未知、沒扣過、已兌過、被竄改、重複、已花費、不確定、跨用途、以及沒有綁定台帳的證明一律拒絕，普通存入絕不能蹭這條路。用途在授權時就綁定（失敗出票與不確定交接是兩種用途），每次認領與重試都要連用途帶四個欄位一起核對；跨用途的認領直接拒絕，不產生副作用，也不會吃掉正確用途的授權。授權只結算一次：已入帳的記為已退款，沒證明結果的記為不確定（保留、不再授權），只有確定沒提交的失敗才會用相同用途釋放同一個授權給重試。票據到底有沒有交到玩家手上無法確認時（地域回呼丟出例外），絕不走上面那條一般退款：不確定交接專用的授權會把序號作廢，並在同一筆儲存交易內退款，一樣免門禁，可兌票據和退款絕不會同時存在。

狀態放在 `<plugin data folder>/security-control.json`，跟資料夾並列，絕不在經濟快照裡。狀態與控制稽核總是一起原子發布（暫存檔加原子移動，再做落盤同步）；替換之前的失敗兩邊都不生效。不支援原子移動的檔案系統會直接拒絕發布，絕不靜默走非原子替換。替換落地之後同步失敗會採用新狀態，絕不謊稱什麼都沒生效。第一次啟動沒有這個檔案會以可寫狀態打開。發布者寫下的每個欄位（format、version、globalReadonly、frozen、audits 裡的 id、操作、操作者、原因、時間與目標）都必須存在、非空、型別精確且 UUID 為規範小寫；缺欄位、空值、型別寫錯、版本號為負或帶小數、未知 format、壞 UUID 或重複 UUID、稽核非法，都會跟損毀檔案一樣 fail-closed，只有未知的額外欄位會忽略相容。檔案損毀、缺欄位或讀不出來就 fail-closed：所有餘額變更都被拒絕，並給出固定的響亮診斷（絕不回顯檔案原文），讀取路徑絕不覆蓋或刪除這個檔案。凍結、解凍、唯讀三條變更在玩家查找之後走共用 IO 執行緒；地域執行緒不拿控制寫鎖也不做落盤同步，指令會立刻返回，真正的回覆只在變更完成後走地域分發發一次。這個 IO 安排只覆蓋控制指令：已通過 mutation permit 的普通同步金流，在控制寫鎖做落盤同步期間仍會等待。這是已接受的線性化代價；慢盤等待量測留給整合驗證（真實 Folia/MySQL/重啟尚未驗證）。執行緒缺失或拒絕會給出明確的型別化拒絕，不改變任何狀態。唯讀開關關不掉讀取失敗，只能修檔案再重啟。`/aceeco reload` 不碰這份控制。普通備份裡沒有它，還原也絕不替換它：要備就停服後另外複製，或走受控的快照匯出。降級到不認識這個檔案的舊版本會失去保護，這是已知取捨，不會靜默橋接。

每次被拒絕的餘額變更動作都只在 `<plugin data folder>/security-control-attempts.jsonl` 留一條最小證據（操作、目標帳號、固定拒絕分類、控制版本、可信操作者、時間）。多帳號的拒絕也只留一條，寫明被凍的目標（全服級拒絕則沒有目標）。完整指令、網路身份、原始原因原文一律不存。追加序列走 IO 執行緒，絕不在地域執行緒上跑；追加失敗會大聲記日誌，記憶體裡的紀錄保留，拒絕照樣成立。記憶體只保留最近 1024 筆，檔案台帳每筆都完整追加。控制稽核和台帳目前都沒有刪除和保留策略：只會一直成長，等管理員自己歸檔。這些紀錄只是隻讀證據，永遠拼不回控制狀態。

可信退款台帳是單服記憶體：重啟會 fail-closed 清空待授權（絕不雙花）。退款證明不了的失敗出票會帶著它的票據（序號、玩家、金額、階段）進入 pending 等人工對帳，絕不盲目重試。

## 整合功能

Vault 與 PlaceholderAPI 都是選用插件。少了其中任何一個，經濟核心依然能跑。Vault 使用設定裡指定的預設貨幣；PlaceholderAPI 使用 `aceeco` 這個命名空間：

```text
%aceeco_balance%
%aceeco_balance_formatted%
%aceeco_balance_<currency>%
%aceeco_balance_<currency>_formatted%
```

Discord 透過 `discord.enabled` 與 `discord.webhook-url` 設定。真正的 webhook 只放在伺服器本機。通知是非同步、盡力而為的：通知出了問題，要和已經完成的交易分開處理。通知沒到不代表錢沒動，先查餘額與交易紀錄。

## 停服、重啟與重新開放

想停服或重啟，請使用平常的服務管理方式，或伺服器主控台指令：

```text
stop
```

請等待世界與插件的保存都完成。重啟之後，先重做一遍每次開服檢查，再讓玩家回來。如果這次重啟是因為上一次重新載入失敗，請先還原最後一份確認正常的設定，免得伺服器反覆用同一份錯誤設定啟動。

## 緊急回退

如果要回溯單筆已經記錄的交易，請從主控台執行：

```text
/aceeco rollback <transaction-id>
```

這條指令僅限主控台，需要 `aceeconomy.admin` 加上 `aceeconomy.admin.rollback`，並且會明確回報每一種結果：成功時會列出回溯審計紀錄的 ID；已經回溯過的交易是安全的無操作；如果標記持久化失敗，代表效果可能已經發生，卻沒有留下持久紀錄。重試之前，請先檢查儲存並人工核對。完整的結果對照表見[指令與權限](commands.zh-TW.md)。

回退指令已經接進正式的指令介面，也有自動化合約測試覆蓋，但真實的線上驗證還沒做完：Folia/Bukkit 橋接的實機執行、真實的 MySQL 儲存，以及用真實資料做的故障注入演練都還沒跑。在這道發布門檻合上之前，請只在事先備好份的受控演練中使用它。

## 把問題交給支援人員

請使用[故障排除](troubleshooting.zh-TW.md)，並提供：最早出現的相關錯誤、版本號、目前儲存類型、已經去掉敏感值的完整指令，以及事件發生的時間。資料檔、備份、密碼、權杖與 webhook 網址都要保密。
