## 选择后端

AceEconomy 通过 JSON 文件或 SQL 后端保存同一套 v2 逻辑数据。JSON 和 SQLite 都放在插件数据目录里；MySQL 则是通过 `storage.mysql.*` 配置的联网数据库。无论选哪种，改变的只是数据的物理存放位置，不会改变[数据库概念与升级](database.zh-CN.md)里说明的账户与交易概念。

| 后端 | 数据位置 | 适合情形 |
| --- | --- | --- |
| JSON | `<plugin-data>/data-v2.json` | 单台服务器，想要一个便于携带的文件。 |
| SQLite | `<plugin-data>/<storage.sqlite.path>` | 单台服务器，想要一个本地 SQL 数据库文件。 |
| MySQL | `host:port/database` 所对应的数据库。 | 已经有一套数据库服务在运行。 |
| MariaDB | 通过 `storage.type: mysql` 配置；没有 `mariadb` 这个值。 | 使用 MySQL 兼容连接方式的 MariaDB 服务。 |

后端在启动时选定。修改 `storage.type` 只会让插件改指另一个存储位置，不会自动复制旧数据，也不会把两个存储合并在一起。

## JSON 文件

当 `storage.type: json` 且数据目录里没有对应文件时，插件会创建 `data-v2.json`。每次数据变动，插件都会先写入一个临时文件，再整体替换成正式文件，因此落盘的是一份完整的文件，而不是写到一半的残破文档。

JSON 模型包含 schema 版本、带余额的账户和交易记录。金额以十进制字符串保存，不会因为浮点格式转换而改变存储下来的数值。

### 安全操作文件

- 复制、替换或移动 `data-v2.json` 之前，必须先停止服务器。
- 除非插件改用了其他受支持的后端，否则文件必须留在插件数据目录内。
- 保留多份带日期的备份，并记录每份备份当时对应的配置。
- 不要手动修改余额或交易记录。

## SQLite 文件

SQLite 使用 `storage.sqlite.path` 指定的路径，该路径在插件数据目录下解析，默认值是 `data-v2.sqlite`。如果解析出来的路径跑出了这个目录（包括用 `..` 往上跳，或使用指向其他根目录的绝对路径），解析器会直接拒绝。

SQL 后端在初始化时会建立 v2 数据表。建立 schema 和写入一批交易记录都包在同一个数据库事务里。重启时，插件会重新打开同一个文件并初始化已有的 schema，不会重复插入版本行。

做文件备份时，先停止服务器，复制 SQLite 文件，再把副本放到正式插件目录之外。还原时则是停止服务器、把选定的文件放回配置路径，然后重新启动服务器。

## MySQL 与 MariaDB

`mysql` 后端会依据 YAML 里的值拼出 `jdbc:mysql://<host>:<port>/<database>`，再把凭证和连接池参数交给 HikariCP，并在这个连接上打开一个 SQL 后端。插件包里已经包含了所需的 JDBC 驱动，本文所说的服务器部署不需要你另外放一个驱动文件。

```yaml
storage:
  type: mysql
  mysql:
    host: "db.example.invalid"
    port: 3306
    database: "aceeconomy"
    username: "<database-user>"
    password: "<set-locally>"
    pool-size: 10
    max-lifetime: 1800000
```

`pool-size` 必须是正数，用来限制连接池的最大连接数。`max-lifetime` 也必须是正数，单位是毫秒。这两个值要放在 `storage.mysql` 之下，而不是作为全局的 `storage` 键。

使用 MariaDB 时，同样保持 `type: mysql`，填入 MariaDB 的主机、端口、数据库、账号和密码即可。配置里没有独立的 `mariadb` 分支。

## 日常运行的安全边界

### 写入与事务

- 单笔交易记录要么被写入，要么被拒绝；重复的交易 ID 不会被悄悄覆盖。
- 一批记录会作为一个数据库事务提交。其中一笔失败时，整批都会回滚。
- 把一笔已有交易标记为「已撤销」可以重复执行，是安全的。
- 进程重启会重新打开同一个存储，不会改选其他后端，也不会迁移数据。

### 受管备份

服务器运行时，使用下面这条标准指令建立一份逻辑快照：

```text
/aceeco backup [label]
```

这条指令只会在插件控制的 `<plugin data folder>/backups` 目录下，写出一份不含任何密码的 v2 JSON 快照。附加的标签（label）只能使用安全的文件名字符。写入时，系统会先以「不存在才建立」的方式生成 `<backup-id>.json`，把完整快照写进去，再以同样方式生成 `<backup-id>.ready`。这个 `.ready` 文件里含有 SHA-256 校验和，是整份快照「正式生效」的标记：还原时必须同时具备 `.ready` 文件，以及与之完全吻合、通过校验的 `.json` 快照。已经存在的快照或标记文件绝不会被覆盖。快照包含逻辑账户、余额、交易、已撤销标记和已用过的一次性序号，但不包含数据库密码或 webhook 网址。移动快照时，请把配对的 `.json` 和 `.ready` 一起搬；只有 `.json` 不算一份已提交的备份。

没有独立的 `/backup` 或 `/restore` 根指令；这些操作只作为 `/aceeco` 的管理子指令存在。指令细节与权限见[指令与权限](commands.zh-CN.md)。

## 还原流程

> **警告：** 还原是破坏性操作。即使快照损坏或不兼容，也绝不能作为删除正式数据的理由。

必须从服务器控制台执行下面这条精确指令：

```text
/aceeco restore <backup-id> confirm
```

这条指令需要 `aceeconomy.admin` 和 `aceeconomy.admin.restore` 两项权限，只要还有任何玩家在线就会拒绝执行，并且只接受小写的 `confirm`。在动到正式数据之前，系统会先做一轮只读预检：检查 JSON 结构、schema 版本、账户与交易记录、重复的交易 ID、金额与时间戳，以及和当前货币配置的兼容性。预检通过后，它会先为当前状态建立一份安全备份；如果这份安全备份失败，还原就会中止，正式状态原封不动。

预检和安全备份都通过后，JSON 还原会通过安全的目录写入机制读取已经提交完成的标记文件与快照配对；这个标记机制是应用层的生效确认，并不依赖系统底层的原子重命名或硬链接。SQLite 与 MySQL 的还原则作为一个 JDBC 事务执行。如果后端出错，系统会如实报告失败，而不会谎称正式数据没有变动。还原成功后，排行榜缓存会被清空，但玩家的会话和界面不会热刷新；让玩家回来之前，请先重启服务器。

## 逻辑层面的后端边界

JSON、SQLite 和 MySQL 之间的逻辑备份与还原，共用同一套 v2 JSON 模型。因此可以做 JSON→JSON、SQLite→JSON→SQLite，以及相应的 MySQL 逻辑路径。但这**不是** MySQL 服务器原生的导出：它不能取代 `mysqldump`、`mariadb-dump`，也不能取代数据库管理员负责的物理／灾难恢复流程。

自动化往返测试已经确认了 JSON→JSON 与 SQLite→JSON→SQLite，涵盖账户、余额、交易、已撤销标记、已用过的一次性序号，以及还原失败时的后端回滚。不过，目前还没有完成真实的 MySQL 连线验证，也没有完成真实的 Folia 备份／还原验证；这些仍属于待做的操作验证项目，本文不会把它们说成已经确认的结果。

## 启动失败时

- 确认 `storage.type` 是三个可接受值之一。
- 使用 SQLite 时，确认 `storage.sqlite.path` 是一个包含 `path` 的 YAML 映射，且解析后的路径仍落在插件数据目录内。
- 使用 MySQL 或 MariaDB 时，检查主机、端口、数据库、用户名、密码和网络连通性。
- schema 版本不匹配，不是改个后端名称就能修好的。请先备份，再按照[数据库概念与升级](database.zh-CN.md)里的 v2 升级说明处理。
