## 选择存储方式

AceEconomy 使用同一套 v2 逻辑数据，但可以选择不同的存放方式：JSON 文件、SQLite 文件，或通过 `storage.mysql.*` 配置的 MySQL 联网数据库。JSON 和 SQLite 都放在插件数据目录里。无论选哪种，改变的只是数据的物理存放位置，不会改变[数据库概念与升级](database.zh-CN.md)里说明的账户与交易概念。

| 存储方式 | 数据位置 | 适合情形 |
| --- | --- | --- |
| JSON | `<plugin-data>/data-v2.json` | 单台服务器，想要一个便于携带的文件。 |
| SQLite | `<plugin-data>/<storage.sqlite.path>` | 单台服务器，想要一个本地 SQL 数据库文件。 |
| MySQL | `host:port/database` 所对应的数据库。 | 已经有一套数据库服务在运行的单台服务器。 |
| MariaDB | 通过 `storage.type: mysql` 配置；没有 `mariadb` 这个值。 | 使用 MySQL 兼容连接方式的 MariaDB 服务的单台服务器。 |

存储方式在启动时选定。修改 `storage.type` 只会让插件指向另一个存放位置，不会自动复制旧数据，也不会把两个存储合并在一起。

## 一份存储只给一台服务器

一份存储只服务一台正在运行的服务器。把两台服务器（或两个插件实例）指向同一个 JSON 文件、同一个 SQLite 文件，或同一个 MySQL 数据库，不在支持范围内。

各后端的写入协调只限于同一个运行中的实例。JSON 后端用实例内的锁串行化写入，再以原子替换发布；两个写入者共用同一个文件时会静默互相覆盖，而每个实例各自沿用内存里的视图，余额与交易记录可能在没有任何错误的情况下分歧。SQL 后端同样没有跨实例的防护，并发写入交错提交时双方都察觉不到。放在网络挂载上的 SQLite 文件，还会叠加挂载本身的锁定行为，插件对此不做任何验证。

> **警告：**插件在启动时不会诊断这种误设。两台服务器指向同一份存储时都会正常启动；损坏要到后来才以丢失或矛盾的记录现形。请在运维上直接避免：一台服务器，一份存储。

多台服务器请各自使用独立的存储（各自的文件，或各自的 MySQL 数据库）；服务器之间搬移数据，只能走受管的 `/aceeco backup` 与 `/aceeco restore` 快照流程。多台服务器共用一份实时存储，需要独立的锁定与世代或防护机制设计，不属于当前存储后端的一部分。

## 锁与世代的容量上限

实例内的锁本身不存条目，只在同一台运行中的服务器里串行化工作。真正随时间增长的是锁旁边的追踪表，以及持久化的历史记录。下面每张有界追踪表共用同一个实测上限 `LockEpochCapacity.MAX_TRACKED_IDS`（10 万个互不相同的 ID）。

| 增长的东西 | 随什么增长 | 上限 | 超过上限时 |
| --- | --- | --- | --- |
| 会话失效世代 | 累计加载过的互不相同的 UUID | 10 万 | 新 UUID 的加载直接失败，错误为 `SessionError.CAPACITY_EXCEEDED`；已有会话不受影响。重启服务器即可重置追踪。 |
| 余额缓存世代 | 累计缓存过的互不相同的拥有者 | 10 万 | 新拥有者走无缓存路径（读请求直接落到存储）；发布返回 `false`。已有拥有者不受影响。 |
| 刷盘失败诊断 | 有未确认刷盘失败的互不相同的 UUID | 10 万 | 会话清理完成后，再记录失败会抛出 `SessionError.CAPACITY_EXCEEDED`。过期条目在下次登录或干净离开时删掉。 |
| SQL 连接池 | 并发使用 SQL 的调用方 | `pool-size`（默认 10） | 借不到连接时先等待，再以明确的超时失败，绝不静默。 |
| 64 位世代计数器 | 失效次数 | 不设上限（有意为之） | 实际不可能溢出：即使每秒失效 100 万次，也有约 29.2 万年的余量。 |

上限的依据：
- **量测范围**：测试预先生成互不相同的 UUID 数组，才记录基准堆内存（`SessionTrackingCapacityMeasurementTest`）。实测差值仅涵盖 Map 条目结构与值对象（新的 `AtomicLong` 实例或共享的 `SessionError` 枚举引用），不包含 UUID 键对象本身的堆内存占用。若将互不相同的键对象（每个约 32 字节）计入，总堆内存占用会进一步增加。
- **测试 JVM 上的观察值**（为实际执行的观察数值，不同 JVM 版本与多次执行会有变动，并非固定保证或最坏情况上界；本节之 MB 均为十进制，1 MB = 1,000,000 字节）：
  - **会话失效世代与余额缓存世代**（`UUID -> AtomicLong`）：10,000 条时观察到约 626 KB（每条约 62.6 字节）；满额 100,000 条时观察到约 7.05 MB（每条约 70.5 字节）。
  - **刷盘失败诊断**（`UUID -> SessionError`）：10,000 条时观察到约 386 KB（每条约 38.6 字节）；满额 100,000 条时观察到约 4.87 MB（每条约 48.7 字节）。
  - **三张表同时满额实测**（两张世代表加一张刷盘诊断表同时填满各 100,000 条）：在测试 JVM 上直接实测，堆内存差值约 20.6 MB（三表合计每 key 约 206 字节），填表耗时视机器与负载而定；本机观察约 60 至 80 毫秒。
- **断言实际保护的门槛**：测试保护的不是固定 MB 总量，而是每条成本的上限门槛：
  - 世代持有者表：100,000 条时严格保护在每条 120 字节以内（10,000 条时为 150 字节以内）。
  - 刷盘诊断表：100,000 条时严格保护在每条 80 字节以内（10,000 条时为 120 字节以内）。
  - 三张表同时满额：三表合计严格保护在每 key 320 字节以内。
  只有成本漂移超过这些门槛时，自动化测试才会报错。
- **完整会话工作集**：10,000 次被追踪的会话加载（账户、快照与持有者条目合计）自动化测试实测装得进 64 MB 堆内存内。
- **持久化已消耗 Nonce**：自动化测试实测第一条消耗新增 61 个 JSON 字符，10,000 条平均每条精确为 61.9999 字符（约 62 字符）。

量测方式说明：于自动化容量测试套件（`SessionTrackingCapacityMeasurementTest`）中执行。测试预先生成互不相同的 UUID 数组，并在记录前后执行多次预热与垃圾回收（GC）稳定堆内存，由回归断言保护每条成本门槛。重启会清掉全部三张追踪表，这是安全的，因为重启后没有还飞着的加载或过期写入。

持久化增长有意不设上限：已消耗的 nonce 与交易历史永不删除，删 key 会破坏 first-writer-wins，删历史会销毁审计证据。请把文件与数据表大小列入日常巡检，服务器之间搬数据只走受管的备份与还原流程。

没有量测、也不做保证的项目：SQLite/MySQL 里的单行存储开销、网络挂载上 SQLite 文件的行为、硬件断电能否存活、真实玩家线程下的堆内存行为。这些仍是待验证的运维事项，不是本指南承诺的保证。

## JSON 文件

当 `storage.type: json` 且目标文件不存在时，插件会自动创建 `data-v2.json`。每次数据变更时，后端均遵循写时复制（Copy-on-Write）原则：
1. **临时写入与强制落盘：** 先于正式文件旁创建临时文件，写入完整快照后执行 `fsync` 强制刷盘。
2. **原子替换（Atomic Move）：** 通过文件系统的原子移动替换目标文件，并同步目录元数据。正式文件永远保持完整快照状态，绝不会出现写入一半的损坏内容。
3. **错误与失败恢复：** 写入中断时会尝试清理临时文件；底层文件系统若不支持原子替换则直接报错，绝不降级为非原子写入。若替换已完成但后续落盘确认失败，系统会将状态标记为已提交，并立即暂停后续写入以防数据分歧，须待重启确认文件。

*注意：本机制之自动化测试仅验证 I/O 异常，未模拟底层硬件断电情境。*

JSON 模型包含 schema 版本、带余额的账户和交易记录。金额以十进制字符串保存，不会因为浮点格式转换而改变存储下来的数值。

### 安全操作文件

- 复制、替换或移动 `data-v2.json` 之前，必须先停止服务器。
- 除非插件改用了其他受支持的存储方式，否则文件必须留在插件数据目录内。
- 保留多份带日期的备份，并记录每份备份当时对应的配置。
- 不要手动修改余额或交易记录。

## SQLite 文件

SQLite 使用 `storage.sqlite.path` 指定的路径，该路径在插件数据目录下解析，默认值是 `data-v2.sqlite`。如果解析出来的路径跑出了这个目录（包括用 `..` 往上跳，或使用指向其他根目录的绝对路径），解析器会直接拒绝。

SQLite 数据库在初始化时会建立 v2 数据表。建立 schema 和写入一批交易记录都包在同一个数据库事务里。重启时，插件会重新打开同一个文件并初始化已有的 schema，不会重复插入版本行。

做文件备份时，先停止服务器，复制 SQLite 文件，再把副本放到正式插件目录之外。还原时则是停止服务器、把选定的文件放回配置路径，然后重新启动服务器。

## MySQL 与 MariaDB

`mysql` 数据库会依据 YAML 里的值拼出 `jdbc:mysql://<host>:<port>/<database>`，再把凭证和连接池参数交给 HikariCP，并在这个连接上打开一个 SQL 数据库。插件包里已经包含了所需的 JDBC 驱动，本文所说的服务器部署不需要你另外放一个驱动文件。

```yaml
storage:
  type: mysql
  mysql:
    host: "db.example.invalid"
    port: 3306
    database: "aceeconomy"
    username: "<database-user>"
    password: "<set-locally>"
    pool-size: 10
    max-lifetime: 1800000
```

`pool-size` 必须是正数，用来限制连接池的最大连接数。`max-lifetime` 也必须是正数，单位是毫秒。这两个值要放在 `storage.mysql` 之下，而不是作为全局的 `storage` 键。

使用 MariaDB 时，同样保持 `type: mysql`，填入 MariaDB 的主机、端口、数据库、账号和密码即可。配置里没有独立的 `mariadb` 分支。

## 日常运行的安全边界

### 写入与事务

- 单笔交易记录要么被写入，要么被拒绝；重复的交易 ID 不会被悄悄覆盖。
- 一批记录会作为一个数据库事务提交。其中一笔失败时，整批都会回滚。
- 把一笔已有交易标记为「已撤销」可以重复执行，是安全的。
- 进程重启会重新打开同一个存储，不会改选其他存储方式，也不会迁移数据。

### 受管备份

服务器运行时，使用下面这条标准指令建立一份逻辑快照：

```text
/aceeco backup [label]
```

这条指令只会在插件控制的 `<plugin data folder>/backups` 目录下，写出一份不含任何密码的 v2 JSON 快照。附加的标签（label）只能使用安全的文件名字符。写入时，系统会先以「不存在才建立」的方式生成 `<backup-id>.json`，把完整快照写进去，再以同样方式生成 `<backup-id>.ready`。这个 `.ready` 文件里含有 SHA-256 校验和，是整份快照「正式生效」的标记：还原时必须同时具备 `.ready` 文件，以及与之完全吻合、通过校验的 `.json` 快照。已经存在的快照或标记文件绝不会被覆盖。快照包含逻辑账户、余额、交易、已撤销标记、已用过的一次性序号和托管出票进度，但不包含数据库密码或 webhook 网址。移动快照时，请把配对的 `.json` 和 `.ready` 一起搬；只有 `.json` 不算一份已提交的备份。

没有独立的 `/backup` 或 `/restore` 根指令；这些操作只作为 `/aceeco` 的管理子指令存在。指令细节与权限见[指令与权限](commands.zh-CN.md)。

## 还原流程

> **警告：** 还原是破坏性操作。即使快照损坏或不兼容，也绝不能作为删除正式数据的理由。

必须从服务器控制台执行下面这条精确指令：

```text
/aceeco restore <backup-id> confirm
```

这条指令需要 `aceeconomy.admin` 和 `aceeconomy.admin.restore` 两项权限，只要还有任何玩家在线就会拒绝执行，并且只接受小写的 `confirm`。在动到正式数据之前，系统会先做一轮只读预检：检查 JSON 结构、schema 版本、账户与交易记录、重复的交易 ID、金额与时间戳，以及和当前货币配置的兼容性。预检通过后，它会先为当前状态建立一份安全备份；如果这份安全备份失败，还原就会中止，正式状态原封不动。

托管出票护栏接着比对线上与候选快照的出票记录：没有出票进度的候选（升级前写下的备份）只在线上没有可兑票时才能整份取代——尚未扣款、尚未交件、已兑换或已作废且无票的线上记录才能回退，这是正式支持的迁移回退路径。线上已有交件、可能已交件、已退款停票或无法判定的记录会整单拒绝，避免余额恢复后背包里的支票仍可兑换或再度可兑换。

已交件或可能已交件的记录，只有在真正完成兑换并标记为已兑换之后，才能解除阻挡。已退款停票与隔离中（无法判定）的记录目前没有正式的解除流程，需要管理员评估后另行处理（例如依事故处置程序），光是处理掉手上的实体票并不保证能回退。若兑换已入账但标记失败（会留下响亮诊断），记录会停在已交件并继续拒绝回退。其他情况下，每条线上托管记录必须在候选中原样存在；候选中新出现且带有扣款证据的记录，必须在同一份快照里附带权威扣款。

普通一次性序号不在这层护栏范围内。还原会把余额与普通序号一起回退，而实体支票放在玩家背包、不在经济快照里，所以护栏不保证还原后的序号永不重复使用。它只保证：还原不会让已交件、可能已交件或已退款停票的托管票在余额恢复后仍可兑换或再度可兑换，还原也不会凭空生出退款。退款或作废只会让票号在账上停用，实体票仍可能留在玩家手上并被再次送入，所以这类记录和已交件记录一样会挡下升级前备份的回退。

预检和安全备份都通过后，JSON 还原会通过安全的目录写入机制读取已经提交完成的标记文件与快照配对；这个标记机制是应用层的生效确认，并不依赖系统底层的原子重命名或硬链接。SQLite 与 MySQL 的还原则作为一个 JDBC 事务执行。如果数据库在还原时出错，系统会如实报告失败，而不会谎称正式数据没有变动。还原成功后，排行榜缓存会被清空，但玩家的会话和界面不会热刷新；让玩家回来之前，请先重启服务器。

交件持久化窗口（已知限制）：托管支票先在地域线程放进玩家背包，之后才在 IO 线程写下交件注记。启动恢复会退还仍停在开始交件的记录，但已读为交件完成的记录永不退款。所以两种先后顺序都很关键：在背包交接之后、交件注记落地之前停掉进程，重启后会退款（若世界存档已先写下票据，票也会留下）；在交件注记落地之后、世界与玩家数据存档之前停掉进程，玩家付了钱却既没有票也拿不到退款。经济快照与世界存档是两套各自的时间点，中间没有共同的原子边界——以上是按目前程序顺序推得的结论，尚未在正式服务器上验证。请正常停服，并等世界与插件存档完成。

## 逻辑层面的存储边界

JSON、SQLite 和 MySQL 之间的逻辑备份与还原，共用同一套 v2 JSON 模型。因此可以做 JSON→JSON、SQLite→JSON→SQLite，以及相应的 MySQL 逻辑路径。但这**不是** MySQL 服务器原生的导出：它不能取代 `mysqldump`、`mariadb-dump`，也不能取代数据库管理员负责的物理／灾难恢复流程。

自动化往返测试已经确认了 JSON→JSON 与 SQLite→JSON→SQLite，涵盖账户、余额、交易、已撤销标记、已用过的一次性序号和托管出票进度，以及还原失败时的数据库回滚。不过，目前还没有完成真实的 MySQL 连线验证，也没有完成真实的 Folia 备份／还原验证；这些仍属于待做的操作验证项目，本文不会把它们说成已经确认的结果。

## 启动失败时

- 确认 `storage.type` 是三个可接受值之一。
- 使用 SQLite 时，确认 `storage.sqlite.path` 是一个包含 `path` 的 YAML 映射，且解析后的路径仍落在插件数据目录内。
- 使用 MySQL 或 MariaDB 时，检查主机、端口、数据库、用户名、密码和网络连通性。
- schema 版本不匹配，不是改个存储方式就能修好的。请先备份，再按照[数据库概念与升级](database.zh-CN.md)里的 v2 升级说明处理。
